# 周度发车机制设计方案（试运行版）

**适用团队：** 产品研发小团队 ｜ **版本：** v0.1 试运行 ｜ **更新日期：** 2026-08-20

---

## 一、目的

试运行阶段只回答三个问题：

1. **每个人下周有活干**——没有空转的人，也没有被遗忘的需求；
2. **每个人知道自己的目标**——任务到人、验收标准前置，周五能明确回答"完成 / 没完成"；
3. **产能被录入**——每个人的负荷以"天"为单位落在表里，排活时有据可依。

**明确不做什么：** 试运行期不用于绩效考核、不做精确工时统计、不引入故事点估算会。所有设计以"阻力最小、先切入工作流"为第一原则。

---

## 二、一周节奏总览

```
周四下班前   周五（发车会）        周一 ~ 周四          周五（验收 + 下周发车）
─────────  ──────────────────  ─────────────────  ──────────────────────
PM 把下周    ① 验收本周任务        成员每天下班前        同左，形成固定节律：
需求写进     （完成/未完成二值）    花 1 分钟更新           一周一班车，
需求池      ② 下周需求拆任务       任务状态               每周五发一班
            ③ 映射到人 + 标档位
            ④ 校验每人负荷 ≤ 5 天
```

每周只有**一个会**（周五，建议 60~90 分钟，验收和发车连着开），平时没有额外仪式，成员唯一的动作是每天更新一次任务状态。

---

## 三、核心规则：颗粒度引导（本方案的灵魂）

### 3.1 档位定义

| 档位     | 含义                 | 使用建议                            |
| -------- | -------------------- | ----------------------------------- |
| **1 天** | 一天内可交付并自验证 | 小改动、修 bug、联调                |
| **3 天** | 半周左右，最常见档位 | 一个完整的功能点                    |
| **5 天** | 独占一整周           | 慎用：一个人一周最多排一个 5 天任务 |

只有三档，不估 2 天、4 天——**粗粒度是故意的设计**：估得越细争论越多，三档足以暴露"装不进一周"的问题。

### 3.2 上车门槛（反向约束产品拆需求）

- **单任务 > 5 天：不允许上车。** 发车会上现场拆，拆不动就退回给 PM，下周再来；
- **Epic 级需求不进周表。** Epic 挂在需求池里，PM 必须切出"本周可交付的切片"才能进表。切片的标准：周五能演示、能验证、能回答完成与否；
- **拆的是交付物，不是代码模块。** 错误示范："优惠券后端表结构设计（3天）"——周五无法验收。正确示范："创建/核销优惠券接口联调通过（3天）"。引导话术：**"这件事周五怎么证明它做完了？"**

### 3.3 产能录入（用档位合计做负荷校验）

- 每人每周默认容量 = **5 天**（请假、外部支持事先扣减，在表里标注）；
- 映射任务时，每人档位合计 **≤ 5 天**，超过即排爆，要么减任务、要么换档位、要么承认这周就排满了；
- 这一步就是"产能录入"的全部——不需要填工时系统，表里的档位合计就是产能数据。

## 四、表结构设计（Excel / 飞书多维表格即可落地）

只用三张表，无权限、无系统、零开发：

### 表 1：需求池（PM 维护）

| 字段     | 说明                      |
| -------- | ------------------------- |
| 需求名称 | 业务语言描述，可以是 Epic |
| 类型     | Epic / 可上车需求         |
| 状态     | 待切片 / 已排期 / 已完成  |
| 目标车次 | PM 期望上车的周次，仅意向 |

### 表 2：周次任务表（每周一个 sheet / 视图，团队共同维护）

| 字段     | 说明                              |
| -------- | --------------------------------- |
| 任务     | 可验收的交付物描述                |
| 所属需求 | 关联需求池                        |
| 负责人   | 唯一，不允许"共同负责"            |
| 档位     | 1 / 3 / 5 天                      |
| 状态     | 未开始 / 进行中 / ✅完成 / 🔁结转 |
| 完成日期 | 状态打勾时随手填                  |
| 验收标准 | 发车会上当场写，一句话            |
| 备注     | 阻塞原因、估偏说明                |

### 表 3：成员产能速览（自动统计，无需手填）

| 成员         | 本周档位合计 | 任务数 | 已完成 | 结转 |
| ------------ | ------------ | ------ | ------ | ---- |
| （自动汇总） | ≤5           | —      | —      | —    |

> 用飞书多维表格时，表 2 加"看板视图"按状态分列，成员每天拖卡片即完成状态更新——这就是低成本的"互动"。

## 五、燃尽思想的最小化落地

不画每日曲线、不要求逐日统计，只保留燃尽图的两个核心动作：

1. **每周一早上总量固定**（本周任务总数写死在表头）；
2. **每天状态真实更新**，表头自动显示"剩余 X / 共 Y"。

周五验收只看二值结果：**完成，或未完成**。不允许"完成了 80%"——80% 的任务 = 未完成任务 = 结转下周。这条规则看似苛刻，但它正是逼出真实颗粒度的机制：完不成的任务下周会被拆得更小。

**结转规则：** 未完成任务自动带入下周任务表并标记 🔁；同一任务**连续结转 2 次**即触发强制复盘提示——要么颗粒度有问题（重新拆），要么存在真阻塞（升级解决）。复盘靠会上提醒，系统不做硬拦截。

## 六、发车会操作步骤（每周五，60~90 分钟）

### 上半场：本周验收（20~30 分钟）

- **谁**：全员
- **如何**：按周次任务表逐条过，负责人说"完成 / 没完成"，主持人当场改状态；完成的任务当场打勾，未完成的标记结转
- **产出**：本周完成率、结转清单

### 下半场：下周发车（40~60 分钟）

- **步骤 1 · 过需求池**：PM 逐条讲下周想上车的需求，Epic 当场切片，切不出可验收切片的退回需求池；
- **步骤 2 · 拆任务**：每条需求拆成 1~5 个可验收任务，任务描述必须能回答"周五怎么证明做完了"；
- **步骤 3 · 映射 + 标档位**：任务指派到唯一负责人，负责人自己报档位（1/3/5），其他人对明显估偏的档位可当场质疑；
- **步骤 4 · 负荷校验**：每人档位合计 ≤ 5 天，超了现场调整；
- **产出**：下周任务表（锁版，本周内原则上不改）。

### RACI 矩阵

| 步骤                  | 执行者 R         | 决策者 A   | 咨询方 C   | 知会方 I |
| --------------------- | ---------------- | ---------- | ---------- | -------- |
| 需求池维护与切片      | 产品经理         | 产品经理   | 研发负责人 | 全员     |
| 主持发车会 / 维护规则 | 研发负责人（你） | 研发负责人 | —          | 全员     |
| 拆任务、报档位        | 各研发           | 研发负责人 | 产品经理   | —        |
| 每日更新任务状态      | 各研发           | 各研发     | —          | 全员     |
| 结转任务复盘          | 任务负责人       | 研发负责人 | 产品经理   | 全员     |

## 七、异常与边界情况

| 场景                        | 处理方式                                                                                                   |
| --------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 周中临时插入紧急需求        | 可以插，但必须**等量换出**：插入 X 天，就从本周移出 X 天任务到需求池。不允许只加不减——否则产能数据立刻失真 |
| 任务做一半发现档位估错了    | **不改档位**，正常做完，备注"估偏"。周五复盘时校准，估偏率本身就是要观察的数据                             |
| Epic 怎么都切不出一周切片   | 允许切成"探针任务"：本周只交付一个技术验证/原型（1~3 天），为下周切片扫清未知数                            |
| 成员请假 / 临时支持其他项目 | 当周容量直接扣减（如容量变 3 天），在产能表里标注                                                          |
| 周五对"是否完成"有争议      | 以发车会上写下的**验收标准**为准——所以验收标准必须当场写、写进表里                                         |
| 有人一周没有任务            | 这是机制要暴露的问题，不是正常现象：要么需求池断了（找 PM），要么任务分配不均（现场调整）                  |

## 八、试运行期指标（只看三个，不看人）

| 指标       | 目标                | 衡量方式                                           | 它回答的问题                   |
| ---------- | ------------------- | -------------------------------------------------- | ------------------------------ |
| 任务完成率 | 试运行期 ≥ 70% 即可 | 完成任务数 / 总任务数                              | 排活是否靠谱                   |
| 结转率     | 逐周下降            | 结转任务数 / 总任务数                              | 颗粒度是否在变好               |
| 档位估偏率 | 逐周下降            | 实际耗时明显超出档位的任务占比（周五复盘定性判断） | 团队对"1/3/5 天"的体感是否校准 |

**纪律：试运行期内这三个指标只用来看机制和流程，不与个人绩效挂钩。** 一旦挂钩，成员会倾向把档位往高报、把任务往小拆，数据立刻失真，机制作废。

## 九、四周试运行路径

| 周次    | 目标                   | 周五会后动作                                                               |
| ------- | ---------------------- | -------------------------------------------------------------------------- |
| 第 1 周 | 跑通流程，允许混乱     | 只记录问题，不改规则                                                       |
| 第 2 周 | 建立"可验收任务"的语感 | 复盘结转任务：是拆大了还是有阻塞                                           |
| 第 3 周 | 校准档位               | 统计估偏率，团队对齐"我们的 1 天到底是多少"                                |
| 第 4 周 | 决定是否常态化         | 回顾三个指标趋势，达标 → 常态化；不达标 → 调整节奏（如改双周发车）再跑一轮 |

## 十、后续工具化的架构思路（仅方向，本期不开发）

试运行的表跑顺之后，如果数据量上来需要产品化，按三层演进，每层都可独立存在：

```
录入层    PM 的需求表单        → 对应：飞书多维表格表单视图（零开发可用）
互动层    成员的任务看板        → 对应：多维表格看板视图，拖卡片改状态
度量层    完成率/结转率/估偏率  → 对应：仪表盘视图，自动汇总
```

关键架构决策只有两个：**单一数据源**（所有视图读写同一张任务表，杜绝多处维护）和**无权限设计**（小团队靠公开透明自治，权限是规模上来之后才需要的东西）。前期飞书多维表格天然具备这三层，零开发；真到需要定制时，再按这三层做轻量 Web 应用即可（已有交互原型可作参考）。
