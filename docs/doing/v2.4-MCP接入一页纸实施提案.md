# v2.4 · MCP 接入一页纸实施提案

> 2026-09-28 立项并拍板。详细工作产出见 `tasks/plan.md`，任务清单见 `tasks/todo.md`。
> 状态：**已立项，未开工**。本文是 `docs/doing/` 规范下的一页纸提案——只锁定边界与决策，实施细节以 `tasks/plan.md` 为准。

## 一、要解决什么

让 AI 编码代理（Claude Code / Mavis / Cursor 等 MCP host）能直接查询 delivery_van 看板数据，并按需执行写操作，**不必手点 AG Grid 或手写 SQL**。

## 二、核心立场

**MCP 是纯适配层，不是第二套业务逻辑。**

所有工具经 tRPC `appRouter.createCaller(ctx)` 执行，复用同一份 zod 校验、同一套业务规则、同一套审计链路径。`api/queries/` 与 `api/queries/tx.ts`、`audit.ts` **一行不改**。

> 为什么不能直连数据层：AGENTS.md 铁律「服务端入参一律 zod 校验」，而校验目前全在 `vanRouter.ts`。直连即绕过校验。走 caller 则一次性白拿校验 + 业务规则（归档锁 / 结转幂等 / 签收守卫）。

## 四、四项已拍板决策

1. **工具 description 用英文**——显式例外于 AGENTS.md「注释与业务文案使用中文」。理由：description 是喂给模型的语料，可能对接英文语境 host。**仅 description 例外**；工具名、参数名、错误文案、代码注释一律中文。
2. **写工具默认不注册**——`MCP_WRITES` 未设时 `tools/list` 不含任何写工具。未注册优于注册后拒绝。开启后写工具强制 `actor` 参数。
3. **不补 stdio**——HTTP 已满足本机与内网，不额外维护薄代理。
4. **工具名用 snake_case**（`van_list`）——不照搬 tRPC 点号路径（`van.list`），点号在部分 MCP 客户端工具名校验中不通用。

## 六、安全边界

- **沿用项目现状：零鉴权**。`/mcp` 与 `/api/trpc` 同端口同进程，**不新增暴露面**。
- **沿用既有禁令：不要暴露公网**（AGENTS.md）。`/mcp` 同受此约束。
- **写工具默认关闭**，是本期最重要的一条安全设计。
- `carry_run` 的不可逆性在 **description 文本中明写**——模型读的是 description，不是 annotations。

## 七、三个必须实测的坑

1. **`vite.config.ts` 的 devServer `exclude` 语义是「不交给 Hono」。** 原式 `^\/(?!api\/).*$` 会把**所有非 `/api/` 路径**（含 `/mcp`）推给 Vite —— 症状是 **dev 下 `/mcp` 404 而 prod 正常**，一个纯本地调试盲区。已改为 `^\/(?!(api|mcp)(\/|$)).*$` 显式放行 api 与 mcp。**这类「dev 挂、prod 好」的问题只有真跑一遍两种模式才暴露**，单测发现不了（单测直接打 Hono 的 `app.fetch`，绕过了 Vite 中间件）。现由 `api/mcp/viteExclude.test.ts` 做回归守卫。
2. **SDK 版本与传输。** 用 v2（`@modelcontextprotocol/server@2.1.0`，2026-07-28 spec 稳定线）+ `createMcpHandler`。**未采用 `@modelcontextprotocol/hono`**——它的 `createMcpHonoApp` 返回独立 Hono app 而非可挂载 handler；`McpHttpHandler.fetch(request)` 直接吃 web 标准 `Request`，Hono 侧一行 `app.all("/mcp", (c) => h.fetch(c.req.raw))` 即可。客户端须同时 `Accept: application/json, text/event-stream`，否则 406；响应是 SSE 帧；工具级入参失败返回 `result.isError=true` + 中文消息（协议层 200），不是 JSON-RPC error。
3. **`ServerContext` 不暴露底层 HTTP Request**（只有 `mcpReq` 的 JSON-RPC 元信息），故 tRPC caller 用合成 Request 占位——已确认无任何过程读取 `ctx.req`，不丢行为。
