## 二、工作包详细设计

### WP1 · 统计三件套（T0.1 / T0.2 / T0.4）——约 1.5 人日

- **Schema**：`tasks` 加 `source TEXT`（enum：`customer` / `platform` / `exploration`，NOT NULL DEFAULT `'customer'`，幂等 ALTER）。存量数据统一回填 customer——**基线期会低估 platform/exploration 占比，接受并在统计面板标注"v2.0 起才有此口径"**。
- **纯函数**（`api/queries/van.ts`，与 `rarityStatsOf` 并列，全部无库可测）：
  - `requesterStatsOf(rows)`：按提出人聚合——提出数、送达数（签收口径）、滞留数（stranded 口径）、UR/SSR 占比、平均在车班数；requester 为空归入"未标注"桶；
  - `rarityInflationOf(rows)`：稀有度 × {done, carried-stranded} 交叉表 + "UR 滞留率 vs N 滞留率"对比行；
  - `sourceStatsOf(rows)`：三方占比 + 各方滞留率。
- **接口**：现有 `stats` procedure 返回体扩展三块（无新端点）。
- **UI**：统计条加三方占比迷你条（三色横条，一眼看结构）；折叠面板放记分卡与通胀报表（AG Grid 同页下方 `<details>` 即可，不引新组件）。
- **测试**：三个纯函数单测（空数组、空 requester、跨班结转的 carryCount 语义——只算 stranded 不算 swap，为 WP3 埋口径）。

### WP2 · 链式审计日志（T0.5）——约 2 人日

- **Schema**：新表（ensureSchema 建表，幂等）：

```sql
CREATE TABLE IF NOT EXISTS audit_log (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts INTEGER NOT NULL DEFAULT (unixepoch()),
  actor TEXT NOT NULL DEFAULT '(unknown)',
  entity TEXT NOT NULL,          -- 'task' | 'member' | 'van' | ...
  entity_id TEXT NOT NULL,
  field TEXT NOT NULL,           -- 变更字段，整行新增记 '*'
  old_value TEXT, new_value TEXT,
  prev_hash TEXT NOT NULL,
  hash TEXT NOT NULL             -- SHA256(prev_hash ‖ 本行全部字段序列化)
);
```

- **写入点**：不改各 procedure 的业务代码，在 `api/queries/` 写操作出口处包一层 `withAudit(actor, entity, fn)` 辅助（connection 层）；覆盖端点清单：快件新增/编辑/删除、状态与送达日期、结转、发新车、成员新增、（WP3 的）签收、（v1.2.0 已有的）拖拽排序。**读操作不记**。拖拽排序涉及 `sort_order` 的批量行更新：按行记录即可（单次拖拽通常只动 1~3 行），若实测噪声大再合并为单条 `entity='tasks-reorder'` 记录——先按简单方案落地。
- **一致性**：better-sqlite3 同步单线程，事务内"读链尾→算 hash→插入"天然串行，无并发断链风险（这点写进代码注释）。
- **校验**：`verifyAuditChain(rows)` 纯函数——重算全链，返回首个断点位置；提供给它周五对账与单测用。
- **actor**：前端每次 mutation 附带当前操作人标签（复用 members；界面已有的"我"的概念或临时手选——**开放问题 5**）；缺省 `'(unknown)'`——软身份，链上可对质即可。
- **UI**：统计区一行只读"日志指纹 `a1b2c3d4`"（链头 hash 前 8 位 + 复制按钮）。
- **锚定仪式（流程，非代码）**：每周五复盘会最后一项，主持人把指纹抄进会议纪要——会后篡改必断链且与纪要不符。
- **测试**：mock DB 单测（链序正确、篡改 old_value 后 verify 报断链、跨 entity 混合写入）。
- **序列化规范（评审补）**：hash 输入的字段序、定界符、NULL 表示在实现时固定并写入代码注释，配一条"锁定序列化格式"的单测——防止后续重构悄悄改格式导致全链校验失效。
- **敏感字段不进链（评审补）**：`note` 等自由文本不记 oldValue/newValue（以 `'(text)'` 占位）——不可篡改日志与数据最小化的折衷：留"变过"的事实，不留内容；否则一条改错的备注将永久无法删除。

### WP3 · 签收制（T1.4）——约 2 人日

- **Schema**：`tasks` 加 `confirmed_by TEXT`、`confirmed_at TEXT`（幂等 ALTER）；**一次性回填**（紧随 ALTER 执行）：`UPDATE tasks SET confirmed_at = done_at, confirmed_by = '(历史)' WHERE status = 'done' AND confirmed_at IS NULL`——存量 done 视同已签收，历史班次完成率不突变；此后新产生的 done 未签收即保持 NULL。
- **接口**：新 procedure `task.confirm(input: { taskId, actor })`——zod 校验：任务必须 `status='done'`、班次未归档（复用 `isVanArchived`）、actor 必须在 members、`requester IS NOT NULL`（无提出人的自驱件**不写库直接视同签收**——统计口径推导，遵守"能推导不落库"）。
- **交互**：done 且未签收的行，提出人格子角标"待签收"，点击即签（一次点击，记 audit）；周五验收会前未签收的 done 件统计条提示"未签收 N 件"，是否结转仍由人决定（二值红线不动：没有百分比）。
- **口径**：完成率与记分卡的"送达"一律改用签收口径；归档班次的存量未签收件（理论上只剩回填遗漏）单独计数展示，不阻塞。
- **测试**：`van.mock.test` 扩展（非 done 不可签、归档不可签、非成员不可签、幂等重签）；e2e 动线（打勾→签收→统计变化→未签收提示→结转）。

### WP4 · 昨日天气（T1.5）——约 0.5 人日

- **纯函数** `suggestedLoadOf(vans, tasks)`：取当前班次之前最近一个班次（按 van 创建时间序），合计其 done（**v1 口径，非签收口径**——见排期节"口径连续性规则"）任务的点数 → 建议装载上限；无历史班返回 null。
- **UI**：统计条一行"建议装载上限 X 点（昨日天气）"；**只提示不拦截**——与运力"仅记录不校验"哲学一致。
- **测试**：纯函数单测（首班无历史、跨月班次序、加班车点数计入下一班天气——为 Phase 2 预留语义）。

### WP5 · 结转原因枚举（决议 5，P2 可顺延）——约 1 人日

- **Schema**：`tasks` 加 `carry_reason TEXT`（enum：`requirement-change` 需求变更 / `blocker` 依赖阻塞 / `estimate` 估算偏差 / `capacity` 产能不足 / `priority` 优先级被挤，可空）。
- **交互**：结转确认时可选下拉（默认空=未分类）；swap 让位原因（Phase 2 引入）届时另加枚举值。
- **统计**：滞留原因瀑布（按班聚合枚举计数，无人名排序）——同时喂记分卡"可控性分层"（requirement-change 归提出人可控，blocker/capacity 归不可控）。
- **测试**：枚举校验单测 + 结转流程带原因的 mock 测试。

### WP6 · 徽章 v1（决议 4）——约 1 人日

- **仅两枚、全自动、实时推导不落库**：
  - 🚚 **整班准点**：本班 stranded 滞留 = 0（团队徽章）；
  - 📦 **送达连击**：某成员连续 2 个班次其负责任务零滞留（个人点亮，无排行）。
- **实现**：`badgesOf(vans, tasks)` 纯函数 + 统计区角标渲染；班次状态变化时 sonner 单次轻提示（无音效——**开放问题 4**）。
- 预言家/让位贡献/无债一身轻随 Phase 2 的预测投票与议价台再上。
- **测试**：纯函数单测（连击跨班语义：中途加入成员、多人负责件）。

### WP7 · 流程与文档——约 1 人日

- 会议纪要模板：固定栏位——链头指纹锚定、三方占比朗读、未签收清单、滞留原因瀑布、（Phase 2 起）还债清单；
- 发车会话术与 `AGENTS.md` 同步更新（签收二拍、昨日天气、隐形机制说明——代理与人同读）；
- E2E 扩展（见 WP3）+ 全量回归；
- 灵魂文档勾选状态同步。

## 三、排期（按班次节奏，Phase 1 合计 9~12 人日含缓冲）

```
第 1 周   迭代 A（2 人日）：WP1 + WP4 ─────────────► 上线即开始基线采集【Gate 0】
第 1~2 周 迭代 B 开发（与基线采集并行，6~8 人日）：WP2 + WP3 + WP6（+WP5 若采纳）
第 2 周   迭代 B 上线 = cutover（回填生效）──► Phase 1 全量，发 v2.0.0（纪要记录 cutover 班次号）
班次 1~4  基线期兼霍桑期：只记录不判定（cutover 落在其中，见下方口径连续性规则）
班次 5~8  判定期：观察指标三态判定 ─────────────►【Gate 1】复盘会评审
Gate 1 后 Phase 2：议价台+预测投票纸面运行（0 开发，纯会议模板）4 班 ──►【Gate 2】决定工具化（v2.1.x）
冻结区解锁：Gate 2 通过 + 对应指标"支持"
```

**关键排期决策**：迭代 B 不等基线满 4 班——开发与采集并行，B 上线时刻即 cutover，回填策略已隔离存量数据。

**口径连续性规则（评审补，防基线断裂）**：cutover 落在基线期中间，指标分两类管理——

- **v1 口径指标**（滞留率、三方占比、稀有度通胀、完成率）：全程沿用 done/carried 定义，从班 1 连续采集，**不因签收上线而改口径**；
- **v2 新增指标**（签收覆盖率、未签收结转占比、昨日天气承诺偏差）：从 cutover 班起算，判定用 cutover 后满 4 班的数据；
- 昨日天气与徽章计算统一用 done 口径（confirmed 仅作为"签收覆盖率"单一指标的数据源）——一处函数一个口径，禁止混用。

## 四、评估门禁（判定规则，来自灵魂文档附 2 M2）

- **三态判定**：指标近 4 班移动平均越过基期中位数 ±1.5×MAD →「支持」/「证伪」，否则「不确定」；判定结果记入会议纪要（rulebook 表未建前的纸面形态）。
- **Phase 1 观察指标**：三方占比、UR+SSR 占比（通胀）、提出人滞留分布、承诺偏差（装载−实际送达）、签收覆盖率、未签收结转占比。
- **毒性信号（触发即回退对应 WP）**：拆单避结转、集体压级、签收扯皮 > 会议时长 20%、"为徽章冲准点"的异常送达质量。
- **混淆控制**：每班打外部冲击标签（故障/假期/大促/人员变动，记在纪要），判定时排除；霍桑期数据不进判定。

## 五、风险与回退

| 风险                        | 缓解                                                         | 回退                                                    |
| --------------------------- | ------------------------------------------------------------ | ------------------------------------------------------- |
| source 存量回填失真         | 面板标注口径起点；基线只看趋势不看绝对值                     | 隐藏列即可，数据无害                                    |
| 签收流于形式（PM 一键全签） | 月度抽查（决议 2）+ 未签收结转的记分卡反馈                   | 隐藏按钮，口径退回 done                                 |
| audit_log 增长              | 每行 <1KB，估算年增 <50MB（千级写/班）                       | 无需回退；如需可按年归档导出                            |
| 霍桑效应                    | 判定期避开前 4 班                                            | —                                                       |
| 机制被无视（无人看统计）    | 三方占比/未签收进周五纪要固定栏位（朗读义务）                | 终极回退：整个 v2 机制下线，v1 行为零损失（全部叠加式） |
| 存量库迁移失败              | 全部幂等 ALTER + 回填 WHERE 限死，可重跑；CI docker job 验证 | 启动即建表逻辑沿用 v1 模式                              |

**总回退原则**：本期所有机制是 v1 行为的**叠加层**，隐藏 UI = 回到 v1，数据保留可再启。

## 六、验收标准（DoD）

1. 本地门禁全绿：`npm test`（含新增 ≥18 条单测）、`npm run test:e2e`（含签收动线）、`npm run check`、`npm run lint`、`npx prettier --check .`；
2. CI 三 job 绿（check / e2e / docker）；
3. 人工动线过检：发新车 → 录件（选 source）→ 送达 → 签收 → 未签收提示 → 结转（选原因）→ 统计面板四块全显示 → 日志指纹可复制 → 徽章点亮 → 归档班次签收被拒；
4. 发版按 v1.0 流程：tag `v2.0.0` → GHCR 镜像 → 数据卷部署（**存量库升级路径必须在发版前用 v1.2.0 数据副本实测一遍**）；
5. 第一个周五：锚定仪式跑通（指纹进纪要）。

## 七、待拍板的开放问题

1. **v2.0 代号**：谱系沿用动漫代号（v1.0 = niulai），建议由你选定——需要预登録进 README 谱系表。
2. **WP5 是否进 Phase 1**：我建议进（量小且是记分卡分层的依赖），但如果要极限压缩迭代 B，它是最合适的顺延项。
3. **actor 的选择交互（迭代 B 开工的前置决策）**：无账号体系下"当前操作人"如何定——(a) 页头常驻"我是谁"单选（一次选择，localStorage 记住）【**默认方案：未否决即按此实现**】；(b) 每次签收时下拉选。这是全应用交互模式的变更，且 WP2 的 actor 传递与 e2e 用例编写都依赖此决策——**迭代 B 开工前必须拍板**。
4. **徽章提示强度**：sonner 单次轻提示 vs 完全静默（只有角标）。
5. **source 列的录入义务人**：谁建件谁选（PM 录客户件、开发录探索件），话术进发车会——默认如此，无开发量，仅确认。

## 八、版本策略

- Phase 1 = **v2.0.0**（机制基座：签收 + 日志 + 天气 + 统计）；
- Phase 2 纸面运行无发版；若 Gate 2 通过后工具化议价台/预测投票 = **v2.1.0**；
- 冻结区各机制按解锁独立小版本（v2.2+），每个都走"纸面 → 门禁 → 工具化"三步，不跳步。
