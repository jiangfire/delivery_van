# v2.2 表格体验优化与多数据库支持计划

> 状态：进行中（2026-09 立项）。版本号 v2.2 为暂定，发版时以实际谱系为准。
> 本文档是实施基准，任务拆解与验收口径以本文为准。

## 背景与需求

四项需求，分两个独立阶段：

- **阶段 A（小）**：看板 AG Grid 表格体验——①横向滚动；②验收标准/备注长文本列默认隐藏 + 开关显示；③长文本自动换行、行高自适应。只动 `src/pages/BoardPage.tsx` 与 `src/index.css`。
- **阶段 B（大）**：数据层从「仅 SQLite」扩展为 SQLite（默认）+ PostgreSQL + MySQL 三方言。核心障碍：现有代码围绕 better-sqlite3 的**同步事务**设计（7 处事务回调同步、`appendAudit` 同步、审计要求业务写+审计同事务），pg/mysql 驱动只支持异步事务，因此必须先做一次「全链路异步化」前置改造，再加方言。

## 关键决策（已与需求方确认）

- 长文本列交互：**默认隐藏 + 表格上方开关显示**。AG Grid Community 版无内置列选择器（ColumnMenu/ColumnsToolPanel 均为 Enterprise），自建两个小开关，命令式调 `api.setColumnsVisible`。
- 数据库：**SQLite + PostgreSQL + MySQL 全部支持**，SQLite 仍为默认与开发主路径。
- **PG/MySQL 环境只在 GitHub Actions**：本地无 PG/MySQL 环境，不做本地连库验证——方言测试一律 env 门控 skip，真实验证完全交给 CI service 容器（任务 9 是阶段 B 的强制验收关卡）。

## 现状关键事实（勘察结论）

- AG Grid 36.1.0 Community，`themeQuartz` Theming API；三个 `flex` 列（title/acceptance/note）导致永不出现横向滚动条；`RowAutoHeight` 在 Community 内无需新依赖；固定列合计 ≈1058px。
- `columnDefs` 引用必须保持稳定（`BoardPage.tsx` 注释红线，重建会销毁编辑器）——显隐切换必须走命令式 api，不能进 columnDefs 依赖。
- SQLite 耦合点：`db/schema.ts`（sqliteTable + `unixepoch()` 默认值）、`api/ensureSchema.ts`（PRAGMA user_version / AUTOINCREMENT / try-ALTER-catch）、`api/queries/connection.ts`（WAL pragma）、`api/queries/van.ts`（7 处同步 `db.transaction`、2 处 `.returning()`——MySQL 不支持 RETURNING）。
- tRPC procedure 本身支持 async，router 层改动小。

## 架构决策

1. **方言选择**：环境变量 `DB_DIALECT=sqlite|postgres|mysql`（默认 sqlite）；`DATABASE_URL` 复用——sqlite 时为文件路径（现状），pg/mysql 时为连接串。
2. **驱动**：PG 用 `postgres`（postgres.js，比 node-postgres 更易被 esbuild bundle）；MySQL 用 `mysql2`。两个驱动打包进 `dist/boot.js`，better-sqlite3 维持 external。
3. **schema 三方言各一份**：`db/schema.ts`（现状 sqlite）+ `db/schema.pg.ts` + `db/schema.mysql.ts`，字段形状手工保持一致；drizzle 不支持跨方言共享定义，不复用不强抽象。时间戳继续存 Unix 秒整数（审计链字节确定性要求），pg/mysql 用 `integer`/`int`，默认值各自方言（`extract(epoch from now())` / `unix_timestamp()`）。
4. **查询层单份、类型泛化**：`api/queries/van.ts` 仍为一份业务代码；在 connection 层定义联合类型与受控 cast（集中在 1 个文件），业务函数签名改为 async。MySQL 无 RETURNING → 收敛一个 `insertReturningId(tx, ...)` helper 按方言分支（mysql 走 insertId）。
5. **ensureSchema 按方言拆分**：PRAGMA user_version 门控在 pg/mysql 下改为 `_dv_meta` 表（key/value）存版本号；DDL 各方言一套（AUTO_INCREMENT / identity）；try-ALTER-catch 模式保留但 catch 按方言错误码忽略。MySQL 的 `text UNIQUE` 限制 → members.name 用 `varchar(191)`。
6. **测试策略**：现有内存 SQLite 测试不动；数据层测试（reorder/confirm/write 模式）抽出可在 PG/MySQL 上重跑的入口，本地无连接串时 skip，CI 用 service 容器跑三方言矩阵。E2E 维持 SQLite。
7. **审计链序列化格式不变**（锁定单测不动），仅 `appendAudit` 变 async 在事务内 await。
8. **事务抽象 `runTx`**（设计修正，2026-09 勘察驱动源码后确认）：better-sqlite3 事务回调只支持同步（传 async 会在首个 await 提前 COMMIT），故 sqlite 路径手写 `BEGIN IMMEDIATE`/`COMMIT`/`ROLLBACK` 包裹 async body（安全性依赖「body 内 await 仅经微任务、无真实 I/O」的铁律，Node 微任务排空前不处理新请求，并发请求插不进来）；pg/mysql 走驱动原生 `db.transaction`。该约定写入代码注释与本文档，违反=审计原子性失效。

### 阶段 B：多数据库支持（M~L 级，严格按序）

- [x] **任务 4（前置）：全链路同步 → 异步化（仍只跑 SQLite）**（2026-09 完成：`api/queries/tx.ts` 落地 runTx，van.ts 全部事务改 `await runTx`，appendAudit 改 async，全量单测 + E2E 绿）
  - **设计修正（勘察驱动源码后确认）**：better-sqlite3 的 `db.transaction` 底层是 `client.transaction(fn)`，回调必须同步——传 async 回调会在首个 await 处提前 COMMIT，静默破坏「业务写+审计同事务」原子性。因此 sqlite 路径不能直接用驱动事务，改为收敛一个 `runTx(db, body)` helper（放 `api/queries/`，供任务 5/8 加方言分支）：
    - **sqlite（保留 better-sqlite3 驱动）**：手写 `BEGIN IMMEDIATE` → `await body(db)` → `COMMIT`，异常 `ROLLBACK` 重抛。安全性依据：body 内的 db 操作在 better-sqlite3 下全部同步返回、审计 hash 用同步 crypto，所有 await 只经微任务队列——Node 在微任务排空前不会处理新请求（宏任务），故并发请求无法插入已开启的事务。**铁律（写进代码注释）：事务 body 内禁止任何真实 I/O 的 await（fetch/定时器等），只允许 await 数据层调用与纯计算。**
    - **pg/mysql（任务 5/8 接入）**：`return db.transaction(body)`（驱动原生异步事务，独立连接，无此约束）。
  - 嵌套事务检查：手动 BEGIN 不支持嵌套，若发现事务 body 内调用了另一个开事务的函数（如结转内联发车），需重构为共用外层事务或 savepoint。
  - `van.ts` 7 处 `db.transaction` 全部改 `await runTx(...)`；`appendAudit` 改 async 并在 body 内 await；van.ts 导出函数全改 async；`vanRouter.ts` await；seed/e2e helpers/测试同步适配。
  - 验收：不改任何业务行为，`npm test`（尤其 van.write.test.ts 审计同事务原子性用例）与 `npm run test:e2e` 全绿。

## 风险与缓解

| 风险                                          | 影响 | 缓解                                                                       |
| --------------------------------------------- | ---- | -------------------------------------------------------------------------- |
| 异步化破坏「业务写+审计同事务」原子性         | 高   | 任务 4 单独成步、现有原子性测试兜底；事务回调内 await appendAudit 逐处核对 |
| drizzle 三方言类型不兼容，strict TS 报错扩散  | 中   | cast 收敛在 dialect.ts 单文件；业务层只面对一个抽象类型                    |
| MySQL 不支持 RETURNING / text 唯一键长度限制  | 中   | insertReturningId helper；members.name 用 varchar(191)                     |
| MySQL 8 与 PG 的 DDL/函数差异（unixepoch 等） | 中   | ensureSchema 按方言独立实现，不追求共享 SQL                                |
| CI 增加 pg/mysql 服务后变慢变脆               | 低   | 仅 check job 加矩阵；health-check 配好；失败与 sqlite 结果分开看           |
| e2e 只覆盖 sqlite，pg/mysql 动线无端到端保护  | 低   | 数据层测试三方言 + CI 容器；e2e 双跑成本高，暂不做                         |

## 明确不做

- 不加 ag-grid-enterprise（列选择器自建两个开关即可）。
- 不引入新 ORM/查询构建器，沿用 drizzle。
- 不动审计链序列化格式与锁定单测。
- e2e 不做三方言矩阵（仅数据层测试覆盖）。
- **pg/mysql 并发 TOCTOU 不修（2026-09 review 决议）**：`carryOver` 幂等检查（事务内快照读）、`addTask` 的 max(sort_order) 读取（事务外）、`isVanArchived` 等前置校验在 pg/mysql 并发下存在竞态窗口——sqlite 靠 BEGIN IMMEDIATE 串行化无此问题，属「方言间并发语义不一致」的已知差异。单实例小团队场景可接受，修复（`SELECT ... FOR UPDATE` / 入库唯一约束兜底）另立任务。
