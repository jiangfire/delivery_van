# 负责人点数制设计方案（v2.5）

> **状态：待评审**（第二版，2026-09-XX 修订）。第一版是「档位分摊」方案（任务档位仍是输入、负责人按份均分/覆盖），**已否决**，理由见 §3。
>
> **前置事实**
>
> - 现状「一个任务多人负责，每人各计全量点数」是 v1 起的**明文设计**（《周度发车机制设计方案.md》§3.3 与 §4 表格），不是 bug。本方案是**口径变更**，不是修 bug。
> - 存量历史周的个人运力数字会变（按均分一次性回填），前后周不可比——见 §10、§12。
>
> **范围**：本方案只做**点数到人**（v2.5），**不动完成与签收的粒度**（仍是一件一勾一签）。
> 「每个负责人各自填完成时间、提出人分别签收」是另一份方案：`docs/doing/个人完成与签收设计方案.md`（v2.6），它建立在本文的 `points` 列之上，**实施顺序是本文在前**。

## 1. 问题

现状实现（`api/queries/van.ts` 的 `weeklyStats`）：

```ts
const mine = rows.filter((t) => t.owners.includes(m.name));
assigned: mine.reduce((s, t) => s + (t.size ?? 0), 0),   // 每人各计全量点数
```

一件 5 点的活挂 2 个人 → 两人运力条各扣 5 点、合计扣 10 点，而整车只装了 5 点。三个后果：

1. **归属失真**：谁被扣多少与该人实际干了多少无关（主力与搭手同额）；
2. **运力系统性虚耗**：名义容量每人 10 点，多人件越多，"已装/上限"越失真；
3. **超载提示失真**：挂名人数越多越容易全员飘红，红条失去信号价值。

## 2. 目标与非目标

**目标**

- 点数归属到**人**：同一件快件上，每个负责人各自一个点数；
- **一个需求有多个负责人参加时，这些人都要各自设置自己的点数**——勾选负责人 ≠ 设置完成：每勾一个人就出现一个只属于他的点数输入框，没填满不算设置完（D5）；
- **任务点数 = 各负责人点数之和**，不再有独立维护的"档位"；
- 未指派负责人的件 = **0 点**（D2），不进任何点数统计；
- 整车口径（昨日天气 / 建议装载上限 / 结转）改为读「各人之和」。

**非目标（明确不做）**

- 不做强制校验或拦截（沿用「运力超载只提示」「稀有度不校验」的现有哲学）；
- 不动**完成与签收的粒度**：本方案下仍是一件一个勾、一个完成日期、一次签收（拆到人见 v2.6 方案）；
- 不动**件数**口径：签收记分卡、徽章连击、滞留率、完成率、三方占比仍按件计，不按点数加权；
- 不做 Phase 2 的让位点数记账（本方案给它留了天然落点：让位 = 把某人的点数改成 0 并把点数交给接替者）。

## 3. 决策记录

| #   | 问题                   | 决策                                                                                   | 理由                                                              |
| --- | ---------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| D1  | 点数语义               | **每人点数制**：每人各填自己的点数，任务点数 = 各人之和                                | 点数归属到人；不存在"总量 vs 分摊"两个互相打架的数字              |
| D2  | 未指派负责人的件       | **0 点，不计入任何统计**                                                               | 模型最干净：点数只有一个来源（负责人行）；代价见 §12              |
| D3  | 存量数据               | **一次性按均分回填进库**                                                               | 历史周运力条不能全变 0；回填后全库单一口径                        |
| D4  | 每人点数范围           | **0~10**（1 点 = 半天，10 点 = 5 天/周），任务合计无上限                               | 与成员运力同口径；0 = 挂名不占运力                                |
| D5  | 每个负责人是否必须设置 | **必须显式设置**：输入框不给默认值，未填满不得「确定」；0 可以，但必须是人显式输入的 0 | 勾选 ≠ 设置完成。若默认 0，漏填就悄悄少算，正是本方案要消灭的失真 |

**被否方案**

- **A「档位 = 任务总点数，负责人分摊（默认均分、可单独改）」**：均分是系统替人拍板，等于又造了一个假的公用量；且"档位"与"分摊合计"两个数字一旦不一致（只提示不拦截），读者不知道信哪个。
- **B′「未指派时保留一个可手填的暂估点数」**：留下一个与个人点数平行的整车字段，同一件上两套数字并存。
- **D3′「存量记 0 / 记 NULL 沿用旧口径」**：前者让历史个人运力全清零；后者让同一周内两套口径并存，统计面板无法解释。

## 4. 数据模型

- **`task_owners` 新增 `points integer NOT NULL DEFAULT 0`**：该负责人在这件上的点数（0~10 整数）。**这是点数的唯一来源。**
  - 列默认值只为「ALTER 补列时存量行必须有值」这个技术需要而设；**运行时语义上点数必须由人显式设置**——API 层 `points` 必填、UI 不给默认值（D5）。
- **`tasks.size` 废弃**：列保留、不读不写（沿用 `pool_items` 的既有惯例——表结构保留但不读写），三份 schema 注释标 `@deprecated`，历史值留给追溯与一次性回填。
- 三份 schema（`db/schema{,.pg,.mysql}.ts`）+ 三份 ensureSchema 同步；`api/schemaDrift.test.ts` 自动覆盖新列，无需改白名单。
- 不加 `(task_id, owner_name)` 唯一约束（现状没有；且历史脏数据会让建索引失败）。数组内重名由 zod `superRefine` 拦。

## 5. 口径（纯函数，唯一来源）

新建 `contracts/points.ts`（前后端共享、无服务端依赖、可无库单测）：

```ts
/** 每人点数上限：1 点 = 半天，10 点 = 5 天（与成员运力同口径） */
export const OWNER_POINTS_MAX = 10;

/** 任务点数 = 各负责人点数之和；无负责人 = 0 */
export function taskPointsOf(owners: { points: number }[]): number;
```

统计、昨日天气、前端「点数」列共用它——一处函数一个口径。

## 6. 读模型

```ts
export type TaskWithOwners = Task & {
  owners: { name: string; points: number }[]; // 单一形状，无平行结构
};
```

- **取消 `taskRowsQuery` 的 `group_concat` 名字聚合**：改为「查 tasks，再查这批 task_id 的 `task_owners` 行，在 JS 里分组」。名字与点数来自同一行，天然对齐——不引入"两个 `group_concat` 恰好同序"这种跨方言脆弱假设。
- 附加收益：负责人聚合不再走 `group_concat`，`connection.ts` 为 mysql 配的 `group_concat_max_len` 截断防护在这条路径上不再需要（实施时确认已无其他调用点再一并清理）。
- `owners` 从 `string[]` 变成对象数组，影响：`badgesOf` 的 `includes`（改 `some(o => o.name === …)`）、MCP 读工具 payload 与描述、前端渲染、既有测试——一次性机械改动。
- **被否备选**：保持 `owners: string[]`、另加平行的 `ownerPoints: Record<string, number>`——两套结构要维持"键集一致"的不变量，成本更高。

## 7. 写模型

`api/schemas.ts`（tRPC 与 MCP 共享的唯一校验来源）：

```ts
export const ownerPointsField = z.number().int().min(0).max(OWNER_POINTS_MAX);
export const ownerAllocInput = z.object({
  name: memberTag,
  points: ownerPointsField,
});
```

`points` 在入参里**必填**（不是 `.optional()`）：服务端不接受"有负责人但没有点数"的行——与 D5 的 UI 必填是同一条规则的两端，前端只是把它做成不填满不能「确定」。

- `taskAddInput` / `taskUpdateInput`：`owners: z.array(ownerAllocInput)` + `superRefine` 拦重名；**移除 `size` 字段**。
- `sizePoints` 及其在 `api/vanRouter.test.ts` 的边界用例 → 换成 `ownerPointsField` 的 0~10 边界用例（`vanRouter.ts` 的历史转发导出同步调整）。
- 数据层 `replaceOwners(tx, taskId, alloc: { name; points }[])`：写 `(task_id, owner_name, points)`。
- 审计：owners 的 diff 值由 `"甲,乙"` 改为 JSON `[{"name":"甲","points":3}]`（与 `taskAuditValue` 同风格）；`taskAuditValue` 去掉 `size`。**只影响新写入的 entry**——历史 entry 字节不变，`serializeAudit` 未动，链完整。
- `carryOver`：结转负责人行时 **points 一起搬**；`toStrandedTask` 不再复制 `size`。
- **破坏性入参变更**：MCP `tasks_add` / `tasks_update` 的 `owners` 形状与 `size` 参数同步改写 description（模型读 description）。

## 8. 统计

- `weeklyStats.byMember.assigned` = Σ 该人的 `points`。
- `suggestedLoadOf`（昨日天气 / 建议装载上限）= 上一班 `status = done` 各件的 `taskPointsOf` 合计（原来是 `Σ size`）。
- **新增** `loadPoints` = 本班全部件 `taskPointsOf` 合计（整车口径）。注意：它按 owner 行求和，若负责人标签里有非成员名字，会大于"成员条之和"。
- 件数口径（`total` / `done` / `carried*` / `completionRate` / `carryRate` / `unconfirmed` / 记分卡 / 徽章）**一律不变**。
- ⚠️ **单位说明（写进统计面板脚注）**：新口径下"点数"= 人·半天投入，整车合计与"每人 10 点运力之和"同单位——「建议装载上限 vs 团队运力」的比较第一次成立（旧口径拿任务级 size 去比个人容量，本来就是混单位）。

## 9. UI

- 档位列 `_size` → 改名**「点数」**，**只读**，值 = `taskPointsOf(owners)`，为 0 时显示 `—`；着色沿用 `sizeBucket` + `.size-badge`（阈值 ≤2 / ≤6 / 更大 仍然有意义）。
- 负责人编辑器（`MultiSelectEditor` + `MultiSelectCellEditor`）——**本方案交互的重心**：
  - 成员列表勾选（同现状，含即时新增非成员标签）；
  - 已选区里**每个人的标签后跟一个只属于他的点数输入框**，`0`~`10`；**不给默认值**（空 = 还没设置）；
  - 面板底部实时显示 `合计 X 点`；只要还有负责人没填点数，就显示 `还有人没设置点数` 并**禁用「确定」**（D5）；
  - `0` 允许（挂名不占运力），但必须是人**显式输入**的 0——空着不算 0；
  - 多人时逐个填（甲 3、乙 2、丙 1），合计即这件快件的点数。
- 只读态单元格渲染：`甲 3 · 乙 2`。
- `+ 快件` 新增的行无负责人 → 0 点，等发车会上定人定点数。
- 统计面板「负责人」页签：运力条走新口径，补一行「整车装载 X 点」。
- `BoardPage.onCellValueChanged`：删除 `_size` 映射与 size 数值化分支；`_owners` 传/收对象数组。

## 10. 迁移与存量回填

**sqlite**（唯一有历史库的方言）：

1. 幂等补列：`try ALTER TABLE task_owners ADD COLUMN points integer NOT NULL DEFAULT 0 catch {}`；
2. `PRAGMA user_version` **2 → 3** 门控的**一次性回填**：对有负责人的件，把旧 `tasks.size` 均分给其负责人（`base = floor(size / n)`，余数按**名字升序**补给前 r 人；`size` 为 NULL → 全 0）；无负责人的件没有 owner 行 → 新口径下 0 点（D2）。
   - 回填逻辑写成可测纯函数 `splitLegacyPoints(size, names)`，定义在 `api/ensureSchema.ts` 并导出，由 `ensureSchema.test.ts` 直接断言（除不尽 / size 为 null / 多人 / 无负责人）。
   - 均分只是回填期的权宜：库里从此只存显式值，不再有推导。

**pg / mysql**：DDL 里带 `points` 列（`DEFAULT 0`）；沿用现状不做补列链与回填——**现存 pg/mysql 库不会自动补列**（见 `api/ensureSchema.pg.ts` 头部注释，与既往所有列变更同款限制）。

**审计链无需迁移**（`serializeAudit` 未变）。`tasks.size` 列保留不删（历史追溯 + 回填依据）。

## 12. 风险与口径断点

| 风险                                                                                                         | 处理                                                                                                                                               |
| ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 历史个人运力数字变小（每人全量 → 均分回填），前后周不可比                                                    | 这正是本次要修的口径；统计面板脚注 + 本文档记一次断点位置                                                                                          |
| **历史上"有档位但没派负责人"的件在新口径下变 0 点**，整车合计与昨日天气随之下降                              | D2 的直接后果。**已盘点（2026-09-28）**：实际只有 2 件 / 19 点，都在已归档的 DV2608D、都不是 done → 不碰任何送达口径，**无需人工补数据**（见 §14） |
| 「点数」列从可编辑变只读，`+ 快件` 后必须先派人                                                              | 用户须知；编辑入口在负责人编辑器里                                                                                                                 |
| **多人件录入变慢**：每个负责人都必须报点、填满才能确定                                                       | D5 的必然代价，也正是"每人各自算"这条要求本身。实现时用 `Tab` 连填、Enter 结束降低摩擦                                                             |
| `owners` 形状破坏性变更（tRPC + MCP 读 payload + 前端）                                                      | MCP description 明写新形状；仓库无外部消费者                                                                                                       |
| 有人拿 0 点负责人当"挂名"滥用                                                                                | 0 点不进运力、不影响统计；与「稀有度不校验」同哲学，不拦截                                                                                         |
| 一次性回填进了"猜的数"（均分），与"能推导不落库"相抵                                                         | 回填后全库单一口径、无 NULL 语义，优于长期双口径；属迁移权宜，非运行时推导                                                                         |
| **过渡期已知状态**：v2.5 上线后、v2.6 之前，完成与签收仍是件级——甲 3 点、乙 2 点，却只有一个完成勾、一次签收 | 这是分版实施的必然窗口（拆分理由见 `个人完成与签收设计方案.md` D1）；v2.6 把完成与验收拆到人后消失                                                 |

## 13. 开放问题

1. 「点数」列在合计为 0 时显示 `—` 还是 `0 点`？
2. `0` 点是否保留？保留 = 有"挂名不占运力"语义；收紧为 `1~10` 则 UI 少了"必须显式填 0"这条绕路，但挂名场景就无处安放。倾向保留。

## 14. 历史库盘点结果（2026-09-28）

只读盘点 `data/delivery_van.db`（`mode=ro`，未写入）。规模：5 班次（DV2608A–E）、4 成员、12 件、25 个负责人行、20 条审计。

→ **看板上"3 人超载"是重复计数造出来的**；按人记之后这一班没人超载。诉求得到实证。
