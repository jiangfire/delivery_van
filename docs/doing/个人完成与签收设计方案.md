# 个人完成与签收设计方案（v2.6）

> **状态：待评审**（2026-09-XX 立项）。承接《负责人点数制设计方案》（v2.5，点数到人）。
>
> **本方案变更的是核心机制条款**：AGENTS.md「送达二值化（没有完成 80%）」「签收制」「滞留只能整件转下一班」三条都会被动到。改动登记见 §2，实施前必须让全员知道周五动作会变。
>
> **建议独立发版**（v2.6）。若与 v2.5 合并发一次，两方案的 schema 变更可合并为一轮 ALTER，但**实施顺序仍是先点数、后完成/签收**（后者依赖前者的 `points` 列）。

## 1. 问题与目标

现状：**完成**（打勾 + 送达日期）与**签收**都是件级——一件一个勾、一个日期、一次签收。

需求：一个需求多个负责人参加时，

- **每个负责人各自填自己的完成时间**（甲 09-05 交，乙还没交）；
- **提出人（PM）对每个人的交付分别签收**（甲的交付验收通过，不等于乙的交付通过）。

## 2. 决策记录（含被否方案）

| #   | 问题                     | 决策                                                                                                              |
| --- | ------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| D1  | 粒度                     | **完成拆到人 + 签收也拆到人**（全拆）                                                                             |
| D2  | 半完成怎么算件级状态     | **全部负责人完成才算 done**，否则整件跟下一班车走——保住「件是承诺、没有完成 80%」的件级口径                       |
| D3  | 被签收的份额跟车时怎么办 | **整件跟车，但已完成并签收的份额在新副本里保持"已完成、已签收"，不重做**；装载按**承诺量**（件点数 = Σ 各人点数） |
| D4  | 件级字段怎么办           | 保留为**叶子数据的物化聚合**，由写路径在同一事务里同步；下游口径与读取点**零改动**                                |
| D5  | 部分完成的份额算不算送达 | **不算**。完成率 / 滞留率 / 昨日天气 / 徽章仍按件（`status === 'done'`）；部分完成只在件内可见                    |
| D6  | 取消完成时签收怎么办     | 取消某人完成 → 作废**该人**的签收（其他人的签收记录保留），件级聚合随之失效                                       |

**D3 解决的那个矛盾**（本方案的设计动因）：若"分别签收"的成果在整件跟车时被抹掉，签收就白签；若按人结转，核心机制的件数口径就崩了。D3 的落点是——**件仍是不可分的承诺，人这一层的完成与验收是真实事实，随件转运时被继承**。

**被否方案**

- **按人结转**（做完的人留本班、没做完的人跟车）：一件会同时出现在两个班次，四态需要新增「部分滞留」，完成率/滞留率/记分卡的件数口径全部要重新定义——冲击机制太大。
- **退回件级**（只拆点数、完成与签收仍是一件一勾一签）：核心机制零改动、立刻能落地，但"甲做完乙没做"在工具里看不出来，个人验收做不了。

## 3. 数据模型

### 叶子：`task_owners` 再加三列

| 列                       | 含义                                                                   |
| ------------------------ | ---------------------------------------------------------------------- |
| `done_at text NULL`      | 该负责人的完成日期（YYYY-MM-DD）；**非空 = 该人已交付**，NULL = 未完成 |
| `confirmed_at text NULL` | 提出人对该人交付的签收日期                                             |
| `confirmed_by text NULL` | 签收人（软身份，惯例是提出人本人）                                     |

> `points` 列由 v2.5 引入（每人自己的点数），本方案不动它。**不再需要额外的布尔完成标记**：`done_at IS NOT NULL` 就是完成（与前端"打勾即记日期、取消即清空"的现有语义同构）。

### 件级：`tasks` 现有字段**全部保留**，语义转为「叶子聚合的物化」

| 件级字段                        | 来源                                                                                                |
| ------------------------------- | --------------------------------------------------------------------------------------------------- |
| `status`                        | `carried` 仍只由结转写入；`done` = 有负责人 且 全部负责人 `done_at` 非空；`todo`/`doing` 仍手动维护 |
| `done_at`                       | 全部完成时 = 最后一个完成者的日期                                                                   |
| `confirmed_by` / `confirmed_at` | 全部签收时写入；否则 NULL                                                                           |

**D4 是这份方案能收敛的关键**：正因为件级字段被物化，`taskStatsOf`（完成率/滞留率）、`suggestedLoadOf`（昨日天气）、`badgesOf`（徽章）、`isConfirmed`（签收口径）、`requesterStatsOf`（记分卡）**全部零改动**——它们继续读件级字段，口径连续性自然成立。

代价是"叶子 + 聚合"有漂移风险，靠两条兜底：

1. **单一写路径**：只有 `updateTask`（负责人状态变更）、`taskConfirm`、`carryOver` 三处会写叶子，聚合重算收敛成一个内部函数，三处都调它；
2. **不变量测试**：每次写后断言「件级聚合 === 叶子聚合」，进三方言共享套件。

## 4. 规则

**完成（每人）**

- 打勾 → 该人 `done_at = today`（沿用 `todayStr()` 的中国时区口径）；取消 → 清空该人 `done_at`，并作废**该人**签收（D6）；
- 日期可手工补录（每人各自的日期）；
- 件级状态列的「完成」下拉**保留为快捷**：勾 = 给全体打同一日期，取消 = 清全体。**单负责人件的行为与现状一字不差**（大多数件是单人）；
- 部分完成时状态列显示 `进行中 · 1/2 人已交`。

**签收（每人）**

- 对**每个人**单独点一次；条件：该人 `done_at` 非空、班次未归档、`actor` 是团队成员（沿用现状校验，不新增强制"必须是提出人"——现状也只是惯例）；
- 幂等：已签收的人重签不覆盖首签；
- 无提出人的自驱件 → **视同签收，不落库**（沿用"能推导不落库"，规则扩展到每人）；
- 件级"已签收" = 全部负责人已签收（或自驱件）→ 由聚合维护，`isConfirmed` 签名不变。

**结转（整件，D3）**

- 整件复制不变；owner 行**连同 `points` / `done_at` / `confirmed_at` / `confirmed_by` 一起复制**；
- 新副本 `status` 仍为 `todo`（它必然有人未完成），承载着已完成份额的记录；
- 源班标记 `carried` 不变（四态仍只由结转写入 `carried`）；
- 装载 = 件点数 = Σ 各人点数（**承诺量**，含已交付份额），口径说明写进统计面板脚注。

## 5. 统计口径

- **件数口径全部不变**：`total` / `done` / `carried*` / `completionRate` / `carryRate` / `remaining` / 昨日天气 / 徽章 / 记分卡；
- `unconfirmed`（未签收）语义微调为「已送达但**尚未全部**签收的件数」；
- **新增（最小）**：负责人页签每行补一个「已交付 x 点 / 共 y 点」（从叶子聚合），不做新面板、不进主界面；
- ⚠️ **必须在统计面板脚注写明**（D5）：**部分完成的份额不计入任何送达口径**——甲交付并签收的 3 点，只要件未完成，就不算本周送达点数，也不进昨日天气。这是「件是承诺」的必然结果。

## 6. UI

- **负责人列**：每个负责人一个 chip，形如 `甲 3 · ✅09-05 · 🔏`；已交付但未签收的 chip 上带「待签收」按钮（点击 = 给这个人签收，actor 取页头「我是谁」）；
- **件级待签收徽标**（现在挂在提出人列）改为汇总显示：只要还有人未签收就显示 `待签收 1/2`；
- **状态列**：完成下拉保留为快捷（全体打勾/取消），旁边显示 `n/m 人已交`；
- **负责人编辑器**（`MultiSelectEditor` / `MultiSelectCellEditor`）：每人一行 —— `点数`（v2.5 已做）+ `完成勾` + `完成日期` + `签收按钮`；
- 提出人列保留「提出人 + 签收汇总」的展示，不再承载签收动作。

> 交互量提示：多人件的周五验收从"点一次签收"变成"逐人签收"。这是全拆的必然成本（§9）。

## 7. 迁移与存量回填

**sqlite**（唯一有历史库的方言）：

1. 幂等补三列：`try ALTER TABLE task_owners ADD COLUMN done_at text catch {}`（`confirmed_at` / `confirmed_by` 同款）；
2. `PRAGMA user_version` **3 → 4** 门控的一次性回填：
   - `tasks.status = 'done'` 的件：把件级 `done_at` 复制给该件的每个 owner 行（历史件是"整件一起交的"，这是诚实近似）；
   - 件级 `confirmed_at` 非空：把 `confirmed_at` / `confirmed_by` 复制给每个 owner 行；
   - 非 done 件（todo/doing/carried）：owner 行三列保持 NULL。

**pg / mysql**：DDL 带三列；沿用现状不做补列链与回填（**现存 pg/mysql 库不会自动补列**，与既往所有列变更同款限制）。

**审计**：owner 行的任何变化（点数 / 完成 / 签收）记一条 `field = owner:<名字>` 的 entry，值用紧凑 JSON（`{"points":3,"doneAt":"2026-09-05","confirmedAt":null}`）；件级聚合字段的变化仍按现有逐字段 diff 记录。`serializeAudit` 未动 → **链完整，无需迁移**。

## 9. 风险

| 风险                                                                   | 处理                                                                 |
| ---------------------------------------------------------------------- | -------------------------------------------------------------------- |
| **周五习惯变更**：多人件从"点一次签收"变成"逐人签收"，当场可能有人漏点 | 件级汇总徽标 `待签收 n/m` 常驻提示；发版时在周会上过一遍动线         |
| 件级聚合与叶子漂移                                                     | 单一重算函数 + 不变量测试（§3）                                      |
| 历史 done 件的每人 `done_at` 用件级日期回填，是近似                    | 回填只用于"历史件每人状态一致"这一事实；历史件本来就无法追溯谁先谁后 |
| 已经交付并签收的份额跟车走，装载按承诺量算 → 装载里含"已交的部分"      | D3 的明确取舍；写进口径脚注（§5）                                    |
| "部分完成"变成日常可见状态，可能诱发"完成 80%"式汇报                   | D5 明确部分完成不进任何送达口径；件级 done 仍是全或全无              |

## 10. 开放问题

1. 逐人签收的入口：只在负责人 chip 上点，还是同时在负责人编辑器里给一排按钮？（倾向前者，编辑器留给点数与完成）
2. 件级「完成」快捷下拉是否保留？保留 = 单人件零变化；去掉 = 强制逐人打勾，更一致但多人件更慢。
3. 已交付并签收的份额跟车后，是否需要"下一班不必重做"的显式提示（如 chip 上标 `（上班已交）`）？
