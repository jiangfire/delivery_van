# 个人完成与签收设计方案 · 实施计划（v2.6）

> **状态：待评审**（2026-10-09 立项并补实施计划）。前置 **v2.5.0 已于 2026-10-09 发布**（点数归属到人），本方案在 `task_owners.points` 之上再加三列。
>
> **本方案变更核心机制条款**：AGENTS.md「送达二值化（没有完成 80%）」「签收制」「滞留只能整件转下一班」三条都会被动到。决策见 §2，实施前必须让全员知道**周五动作会变**。
>
> **独立发版 v2.6**（本方案不动 v2.5 已发布的东西，只加列 + 加动作）。文档按项目惯例留在 `docs/doing/`，实施完移入 `docs/archived/`（项目用 docs 生命周期，不再用 `tasks/`）。

## 1. 问题与目标

现状：**完成**（打勾 + 送达日期）与**签收**都是件级——一件一个勾、一个日期、一次签收。

真实场景（v2.5 上线后立刻出现）：一件 14 点的活由 4 个人做（丰 3 / 李 7 / 王 2 / 刘 2）。周五：
李交了自己的那份，丰和刘还没交。现在工具里只能"整件未完成"——**李交付并验收过的那 7 点在系统里没有任何痕迹**，下周整件跟车时也没人说得清哪部分做过。

目标：

- **每个负责人各自填自己的完成时间**（李 10-03 交，丰还没交）；
- **提出人（PM）对每个人的交付分别签收**（李的交付验收通过 ≠ 丰的交付通过）；
- 交付与验收的事实**跟着件走**：整件跟下一班车时，已交付已签收的那份不会被抹掉、不用重做。

## 2. 决策记录

### 2.1 机制决策（已定）

| #   | 问题                     | 决策                                                                                                              |
| --- | ------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| D1  | 粒度                     | **完成拆到人 + 签收也拆到人**（全拆）                                                                             |
| D2  | 半完成怎么算件级状态     | **参与判定的负责人全部完成才算 done**，否则整件跟下一班车走——保住「件是承诺、没有完成 80%」的件级口径             |
| D3  | 被签收的份额跟车时怎么办 | **整件跟车，但已完成并签收的份额在新副本里保持"已完成、已签收"，不重做**；装载按**承诺量**（件点数 = Σ 各人点数） |
| D4  | 件级字段怎么办           | 保留为**叶子数据的物化聚合**，由写路径在同一事务里同步；下游口径与读取点**零改动**                                |
| D5  | 部分完成的份额算不算送达 | **不算**。完成率 / 滞留率 / 昨日天气 / 徽章仍按件（`status === 'done'`）；部分完成只在件内可见                    |
| D6  | 取消完成时签收怎么办     | 取消某人完成 → 作废**该人**的签收（其他人的签收记录保留），件级聚合随之失效                                       |

**D3 解决的那个矛盾**（本方案的设计动因）：若"分别签收"的成果在整件跟车时被抹掉，签收就白签；若按人结转，核心机制的件数口径就崩了。D3 的落点是——**件仍是不可分的承诺，人这一层的完成与验收是真实事实，随件转运时被继承**。

### 2.2 实施细节决策（本次补，含两处新增边界）

| #   | 问题                           | 决策                                                                                                                                                                                                                   | 理由                                                                                            |
| --- | ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| D7  | 件级 `done_at` 取谁的日期      | **最后一个完成者的日期**                                                                                                                                                                                               | 件真正闭环的时刻                                                                                |
| D8  | 件级「完成」下拉快捷是否保留   | **保留**：勾 = 给参与判定的全体打同一天，取消 = 清全体                                                                                                                                                                 | **单负责人件（多数）行为与现状一字不差**；多人件想分开交时才进编辑器                            |
| D9  | 件级 `status` 是否自动变化     | **首次有参与判定的人完成 → `todo` 自动升 `doing`；不自动回落**（取消后保持 `doing`，人可手动改回）                                                                                                                     | 有人交了就事实在进行中；不做"是否自动升过"的记账                                                |
| D10 | 打勾与签收分别放哪             | **打勾**：件级快捷（状态列）+ 负责人编辑器逐人；**签收**：负责人 chip 上的「签收」按钮（点一次签一个人）                                                                                                               | 打勾高频（周五常态一键），签收是 PM 的慎重动作、要能逐个点                                      |
| D11 | **0 点负责人是否参与完成判定** | **不参与**：参与判定的集合 = 该件上 `points > 0` 的负责人。**退化规则**：一件有 owner 行但全是 0 点时，集合退化为全部 owner（否则全挂名件既不能闭环、也永远签不掉，成死结）；一件完全没有 owner 行时完全手动（见 D12） | 0 点 = 挂名不占运力，不该阻塞件闭环；但"空集"与"全 0"必须显式区分，否则要么自动化事故、要么死结 |
| D12 | 无负责人的历史 `done` 件怎么办 | **不推导、不降级**：没有 owner 的件，件级 `status`/`done_at` 完全由手动维护，聚合重算跳过它                                                                                                                            | 历史库里有"没派人也标了完成"的件，不能被新规则降级成未完成                                      |
| D13 | 审计字段怎么记                 | owner 行的任何变化（点数 / 完成 / 签收）记一条 `field = owner:<名字>` 的 entry，值用紧凑 JSON `{"points":3,"doneAt":"2026-10-03","confirmedAt":null}`                                                                  | 与既有 owners 的 JSON 值同风格；链上可对质到人                                                  |
| D14 | 改负责人列表会不会抹掉交付记录 | **同名保留**：替换负责人列表时，名字没变的人**保留其 `done_at` / `confirmed_at` / `confirmed_by`**                                                                                                                     | 现 `replaceOwners` 是删了重插；不特殊处理则"改个点数就抹掉交付与签收"                           |

### 2.3 被否方案

- **按人结转**（做完的人留本班、没做完的人跟车）：一件会同时出现在两个班次，四态需要新增「部分滞留」，完成率/滞留率/记分卡的件数口径全部要重新定义——冲击机制太大。
- **退回件级**（只拆点数、完成与签收仍是一件一勾一签）：核心机制零改动、立刻能落地，但"李做完丰没做"在工具里看不出来，个人验收做不了。
- **新增「展开行」详情面板承载逐人完成/签收**：交互路径更长（展开 → 找行 → 点），且 AG Grid 主从表要重构；现用的"chip + 编辑器"已够用。

## 3. 数据模型

### 3.1 叶子：`task_owners` 再加三列（v2.5 已有 `points`）

| 列                       | 类型                                  | 含义                                            |
| ------------------------ | ------------------------------------- | ----------------------------------------------- |
| `done_at text NULL`      | sqlite/pg `text`，mysql `varchar(16)` | 该负责人的完成日期（YYYY-MM-DD）；非空 = 已交付 |
| `confirmed_at text NULL` | 同上                                  | 提出人对该人交付的签收日期                      |
| `confirmed_by text NULL` | sqlite/pg `text`，mysql `varchar(64)` | 签收人（软身份，惯例是提出人本人）              |

**不需要额外的布尔完成标记**：`done_at IS NOT NULL` 就是完成（与前端"打勾即记日期、取消即清空"的现有语义同构）。

三方言 DDL 与幂等补列（`db/schema{,.pg,.mysql}.ts` 与 `api/ensureSchema{,.pg,.mysql}.ts` 同步，`api/schemaDrift.test.ts` 兜底）：

```sql
-- sqlite / pg：CREATE TABLE IF NOT EXISTS 里追加
done_at text, confirmed_at text, confirmed_by text
-- mysql
done_at varchar(16), confirmed_at varchar(16), confirmed_by varchar(64)
```

```ts
// sqlite 旧库幂等补列（与 points 同款）
try {
  db.run(sql`ALTER TABLE task_owners ADD COLUMN done_at text`);
} catch {}
try {
  db.run(sql`ALTER TABLE task_owners ADD COLUMN confirmed_at text`);
} catch {}
try {
  db.run(sql`ALTER TABLE task_owners ADD COLUMN confirmed_by text`);
} catch {}
```

### 3.2 件级：`tasks` 现有字段**全部保留**，语义转为「叶子聚合的物化」

| 件级字段                        | 来源                                                                                                                                            |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `status`                        | `carried` 仍只由结转写入；`done` = **参与判定集合非空** 且 集合内全部 `done_at` 非空；`todo`/`doing` 仍手动维护（仅按 D9 从 todo 单向升 doing） |
| `done_at`                       | 全部完成时 = 最后一个完成者的日期（D7）                                                                                                         |
| `confirmed_by` / `confirmed_at` | 参与判定集合内**全部**已签收时写入（取最后一次签收的 actor 与日期）；否则 NULL                                                                  |

**D4 是这份方案能收敛的关键**：件级字段被物化后，`taskStatsOf`（完成率/滞留率）、`suggestedLoadOf`（昨日天气）、`badgesOf`（徽章）、`isConfirmed`（签收口径）、`requesterStatsOf`（记分卡）**全部零改动**——它们继续读件级字段，口径连续性自然成立。

### 3.3 聚合不变量（唯一重算入口）

一个内部函数（`api/queries/van.ts`，不导出给路由）承接全部件级聚合写入：

```
recomputeTaskAggregate(tx, taskId):
  leaves ← 该件所有 owner 行
  if leaves 为空: 什么也不做 —— 无 owner 的件件级字段完全手动（D12）
  judged ← leaves where points > 0；若 judged 为空（全是 0 点）则 judged ← leaves（D11 退化规则）

  allDone      = judged.every(o => o.done_at != null)
  allConfirmed = judged.every(o => o.confirmed_at != null)
  有人完成     = judged.some(o => o.done_at != null)

  status ← allDone                  ? 'done'      // D2：参与判定的人全交完才算闭环
         : 原 status === 'carried'  ? 'carried'   // 归档只读，不参与推导
         : 原 status === 'done'     ? 'doing'     // 有人取消了完成 → 回落
         : 有人完成                 ? 'doing'     // D9：首次有人完成，todo 单向升 doing
         : 原 status
  done_at ← allDone ? max(judged.done_at) : null                                  // D7
  confirmed_* ← allConfirmed ? 取 leaf 中 max(confirmed_at) 那条的 {by, at} : {null, null}
```

两条兜底纪律：

1. **单一写路径**：只有 `updateTask`（负责人/完成变更）、`taskConfirm`、`carryOver` 三处写叶子，三处都在同一事务里调这个函数；
2. **不变量测试**：每次写后断言「件级聚合 === 由叶子推导的期望值」，进三方言共享套件（`van.*.suite.ts`）。

## 4. 规则（含边界）

**完成（每人）**

- 打勾 → 该人 `done_at = today`（沿用 `todayStr()` 的中国时区口径）；取消 → 清空该人 `done_at`，并作废**该人**签收（D6）；
- 日期可手工补录（每人各自的日期）；
- 件级状态列的「完成」下拉保留为快捷（D8）：勾 = 给参与判定全体打同一日期、取消 = 清全体；
- 部分完成时状态列显示 `进行中 · 1/2 人已交`（分子 = 已完成的参与判定人数）。

**签收（每人）**

- 对**每个人**单独点一次（D10）；条件：该人 `done_at` 非空、班次未归档、`actor` 是团队成员（沿用现状校验，**不新增强制"必须是提出人"**——现状也只是惯例）；
- 幂等：已签收的人重签不覆盖首签；
- 无提出人的自驱件 → **视同签收、不落库**（沿用"能推导不落库"，规则扩展到每人）；
- 件级"已签收"由聚合维护（§3.2），`isConfirmed(task)` 签名不变。

**改负责人列表（D14）**

- 替换列表时按名字对齐：名字仍在的人**保留三列**，新名字三列 NULL，被移除的人整行删除；
- 点数可改（v2.5 语义不变：改点数不影响完成/签收记录）。

**结转（整件，D3）**

- 整件复制不变；owner 行**连同 `points` / `done_at` / `confirmed_at` / `confirmed_by` 一起复制**；
- 新副本 `status` 仍为 `todo`（它必然有人未完成），但带着已完成份额的记录；
- 源班标记 `carried` 不变（四态仍只由结转写入 `carried`），源班的 owner 行原样保留（历史事实）；
- 装载 = 件点数 = Σ 各人点数（**承诺量**，含已交付份额），口径说明写进统计面板脚注。

## 5. 统计口径

- **件数口径全部不变**：`total` / `done` / `carried*` / `completionRate` / `carryRate` / `remaining` / 昨日天气 / 徽章 / 记分卡；
- `unconfirmed`（未签收）语义微调为「已送达但**参与判定集合尚未全部**签收的件数」；
- **新增（最小）**：负责人页签每行补一个「已交付 x / y 点」（x = 该人已完成的份额点数合计，y = 该人分配到的点数合计），不做新面板、不进主界面；
- ⚠️ **必须在统计面板脚注写明**（D5）：**部分完成的份额不计入任何送达口径**——李交付并签收的 7 点，只要件未完成，就不算本周送达点数、也不进昨日天气。这是「件是承诺」的必然结果。

## 6. UI

**看板（行内）**

```
负责人列（每人的状态一屏可见；未交的人只有名字 + 点数）
  丰智娟 3 · 王思雨 2 · 李子烨 7 ✅10-03 🔏 · 刘洋 2 ✅10-05 [签收]
状态列  进行中 · 2/4 人已交        ← 参与判定 4 人里 2 人已交；全交完变「完成」
提出人列 比屋定 · 待签收 2/4        ← 件级汇总徽标；本列不再承载签收动作
```

- chip 内容：`名字 点数` + 若已交付 `✅MM-DD` + 若已签收 `🔏`；
- 已交付未签收的 chip 尾部一个小「签收」按钮（actor 取页头「我是谁」）；
- **chip 本身不可点**（避免误触）；打勾与改日期在编辑器里做；
- 件级「待签收 n/m」汇总徽标移到提出人列（现在那里的单件级「待签收」按钮迁走）。

**负责人编辑器**（`MultiSelectEditor` / `MultiSelectCellEditor`）——沿用 v2.5 的三条交互约定（行内输入、看见后果、放弃要说话）：

```
勾选负责人，给每个人设点数，并各自打勾完成
☑ 李子烨   7/10  [ 7 ] →14 ⚠   [✓完成] [10-03]   ← 完成勾 + 日期（可手改）
☐ 王思雨   2/10  [   ]         [     ] [     ]   ← 没勾的人不参与判定
☑ 刘洋     2/10  [ 2 ] →4      [✓完成] [10-05]
合计 14 点 · 2/4 人已交                          [确定]
```

（`→N` 是 v2.5 已有的"加上这件后的个人已装"预览；`⚠` 表示会压超上限。）

**交互量提示**：多人件的周五验收从"点一次签收"变成"逐人签收"（n 次）。这是全拆的必然成本；D8 让**打勾**的常态路径仍是 1 步。

## 7. 迁移与存量回填

**sqlite**（唯一有历史库的方言）：

1. 幂等补三列（§3.1）；
2. `PRAGMA user_version` **3 → 4** 门控的一次性回填（沿用 v2.5 的 `backfillOwnerPoints` 写法，新增 `backfillOwnerDelivery`）：
   - `tasks.status = 'done'` 的件：把件级 `done_at` 复制给该件的每个 owner 行（历史件是"整件一起交的"，这是诚实近似）；
   - 件级 `confirmed_at` 非空：把 `confirmed_at` 复制给每个 owner 行，`confirmed_by` 取件级值、缺省 `'(历史)'`（与 v2.0 的签收回填同口径）；
   - 非 done 件（todo/doing/carried）：owner 行三列保持 NULL；
   - **无 owner 的件不产生任何行**（D12：它们不参与聚合推导）。

**pg / mysql**：DDL 带三列；沿用现状不做补列链与回填——**现存 pg/mysql 库不会自动补列**（与既往所有列变更同款限制，v2.5.0 已因此发过升级提示），需手工：

```sql
ALTER TABLE task_owners ADD COLUMN done_at text;
ALTER TABLE task_owners ADD COLUMN confirmed_at text;
ALTER TABLE task_owners ADD COLUMN confirmed_by text;
```

**审计**：`serializeAudit` 未动 → **链完整，无需迁移**；owner 行变化按 D13 记 `owner:<名字>`。

## 10. 风险与回滚

| 风险                                                 | 影响 | 处理                                                               |
| ---------------------------------------------------- | ---- | ------------------------------------------------------------------ |
| **周五习惯变更**（多人件逐人签收）                   | 高   | D8 让打勾保持一键；「待签收 n/m」常驻提示；发版时周会过动线        |
| 件级聚合与叶子漂移                                   | 高   | 单一重算函数 + 每个写用例都断言不变量（§3.3）                      |
| **改负责人列表抹掉交付记录**（删了重插）             | 高   | D14 同名保留；套件专门覆盖"改点数后 done/签收仍在"                 |
| 历史 done 件的每人 `done_at` 用件级日期回填，是近似  | 低   | 回填只表达"历史件每人状态一致"这一事实；历史件本来无法追溯谁先谁后 |
| 无 owner 的历史 done 件被新规则降级                  | 中   | D12 显式排除；回填与聚合都跳过这类件，并有专门用例                 |
| 装载按承诺量算，含"已交的部分"                       | 中   | D3 的明确取舍；写进口径脚注（§5）                                  |
| "部分完成"变成日常可见状态，可能诱发"完成 80%"式汇报 | 中   | D5 明确部分完成不进任何送达口径；件级 done 仍是全或全无            |

**回滚**：本方案只**加列 + 加动作**，不动 v2.5 已发布的数据语义。回滚 = 回退代码版本（列留着不读不写，与 `tasks.size` 同处理）；`user_version` 停在 4 不影响旧代码（旧代码不读 `task_owners` 的三列）。**不需要反向迁移**。

## 11. 开放问题（需你拍板）

1. **0 点负责人要不要能在件上"打勾完成"？** 现决策 D11 是"0 点不参与完成判定"——那他们的完成勾就只是个人留痕、对件级无影响。要不要干脆**禁止 0 点的人打勾**（UI 置灰）？倾向：允许（挂名的人真参与了也不该被系统拦，只是不阻塞件的闭环）。
2. **`done_at` 为空但有签收记录**要不要拦住？现规则是"必须先打勾才能签收"，历史回填也不会造出这种行。倾向：不额外加约束，靠写路径保证。
3. **件级「完成」快捷在多人件的语义**：勾 = 给全体打同一天（含未实际交付的人）。这会被误用成"一键宣称全交"吗？倾向：保留（D8），但确认框写明"将给 N 位负责人打同一日期"。
