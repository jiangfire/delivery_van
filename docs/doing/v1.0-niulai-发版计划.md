# v1.0「niulai」发版计划

> 关联文档：`docs/周度发车机制设计方案.md`（业务机制，核心思路）、`docs/archived/任务大厅与稀有度分级设计方案.md`（稀有度体系，已实施）、`docs/archived/v1.0-niulai-评审决策存档.md`（评审结论）。
> 数据库尚在发版前阶段，**无存量数据兼容负担**，schema 调整自由。

## 一、版本范围

v1.0 交付一个可投入试运行（机制设计方案第九章四周路径）的完整工具：

- **班次体系**：DV 编码班次（单月最多 26 班，A–Z）、手动「发新车」创建班次（不绑定周五）、班次切换 + 历史跳转
- **周任务表**：AG Grid 行内编辑、三档粒度（1/3/5 天）服务端强制、送达二值化 + 送达日期可补录、行内删除
- **成员产能**：成员为永久标签（不可删除）、运力仅做记录、产能速览按标签自动聚合统计
- **快件模型（委托已合并）**：委托/任务大厅概念并入快件，一套数据模型（标题/稀有度/提出人/负责人/档位/送达二值/验收标准/备注），表格内「+ 快件」新增、行内编辑、行内删除；`pool_items` 表保留但废弃不再读写
- **稀有度体系**：六级稀有度（普通/优秀/稀有/史诗/传说/神话）直接标在快件上、整体文字着色（神话彩虹动画）、颜色只是标记不做筛选不做拦截
- **滞留结转**：一键转下一班（仅允许紧邻班次，目标班不存在时自动创建）、事务包裹 + 幂等防重、≥2 班强制复盘提示、**结转后整班归档只读**（服务端 `isVanArchived` 校验 + 前端禁用编辑）
- **统计条**：未送达 X / 共 Y、送达率、滞留率、强制复盘数、稀有度构成（机制设计方案第八章三指标之二；估偏率靠备注 + 复盘定性）

明确不做（与机制设计方案对齐）：无账号无权限（谁都能改的看板）、无绩效挂钩、无精确工时、无故事点。

## 二、质量门禁与 CI

- 本地门禁：`npm test`（73 用例）、`npm run test:e2e`（Playwright，14 用例）、`npm run check`、`npm run lint`、`npx prettier --check .`，提交前必跑（纯后端改动可跳过 e2e）。
- **GitHub Actions**（`.github/workflows/ci.yml`，push/PR 触发）：
  - `check` job：prettier --check → eslint → tsc → vitest
  - `e2e` job：安装 Chromium 跑 `npm run test:e2e`，失败上传 playwright-report
  - `docker` job：`docker build` + 容器冒烟（首页 200、`/api/trpc/ping` 返回 ok）——本机无 Docker 环境，镜像构建正确性由 CI 保证。

## 三、发版步骤

1. [ ] 确认 main 上 CI 全绿（check + e2e + docker 三个 job）
2. [ ] `npm run dev` 人工过一遍核心动线：发新车 → + 快件 → 标稀有度/提出人 → 勾选负责人 + 档位 → 打勾送达 → 滞留转下一班 → 班次跳转 → 归档只读生效 → 统计条与稀有度构成显示
3. [ ] 打 tag：`git tag v1.0.0 && git push --tags`
4. [ ] 部署：`docker build -t delivery_van . && docker run -p 3000:3000 -v delivery_van_data:/app/data delivery_van`（**必须挂数据卷**，见 README）
5. [ ] 按机制设计方案附录「第一周启动检查单」启动试运行

## 四、发版验收标准

- CI 两 job 全绿；容器首次启动自动建表、重启数据不丢（数据卷验证）
- 第一周试运行结束能回答：「每个人是否都清楚自己下周要干什么？」

## 五、发版后路线

稀有度体系、班次模型重构与委托合并（任务大厅并入快件）已全部合入 v1.0，无 v1.1/v1.2 遗留项。后续待定：

- E2E 覆盖扩展（更多边界交互：结转幂等重试、班次编码边界等）
- 班次编码在 2100 年绕回（`% 100` 两位年），理论问题，到时再说
